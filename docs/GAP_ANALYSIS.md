# 목표 사이트 대비 격차 분석

작성일: 2026-08-31 · 상태: v1 · 상위 문서: [PLAN.md](PLAN.md) · 관련: [REQUIREMENTS.md](REQUIREMENTS.md), [IDEAS.md](IDEAS.md)

비교 대상: **https://visualbaseball.com/** (이하 "목표 사이트")
비교 시점의 우리: React 앱 6페이지 + 레거시 `web/` 12페이지 + FastAPI 25 엔드포인트.

## 조사 방법과 한계

- 목표 사이트는 9개 네비 항목 중 **9개 전부**(`/`, `/schedule`, `/standings`, `/batting`, `/pitching`, `/distance`, `/attendance`, `/gametime`, `/daily`)를 실제로 fetch했다.
- **확인 못 한 것**: `/rules` 및 그 하위(`/rules/3.05` 등)는 fetch하지 않았다. 홈에서 링크만 확인했다.
- **신뢰도 한계**: 목표 사이트는 클라이언트 렌더링으로 보인다 — `/schedule`은 지표 자리가 전부 `—`(placeholder)로 왔다. 따라서 아래 "목표 사이트에 있는 것" 목록은 **페이지에 박혀 있는 차트 제목·표 헤더·필터 라벨** 기준이며, 각 차트가 실제로 어떤 값을 그리는지까지는 검증하지 못했다. 기능 인벤토리로는 신뢰할 수 있으나, 렌더링 품질 비교는 아니다.
- 우리 쪽은 `web/`의 html·js 12개, React `pages/`·`components/` 전부, `data/raw`·`data/processed` 실제 헤더와 행수, `backend/routers/analytics.py`·`migrate.py`를 직접 읽었다.
- 목표 사이트의 코드·에셋은 열람하지 않았고 복제하지 않았다. 기능과 시각화 **방식**의 대조까지다.

## 1. 한 줄 결론

**가장 크게 비어 있는 것은 "화면당 깊이"다.** 목표 사이트는 탭 하나가 표 3종 + 차트 15~19종인데 우리는 탭 하나가 표 1개다 — 그리고 이 격차의 대부분은 **새 데이터가 아니라 이미 디스크에 있는 컬럼을 안 그린 것**이다(순위표의 홈/원정·연속·최근10, `player-stats`의 wRC+·WPA·WAR, 15만 행 투구 데이터의 `PitchType`·`SpeedKmh`). 반대로 목표 사이트를 절대 따라갈 수 없는 영역도 명확하다: 무브먼트·릴리스포인트, 경기 단위 소요시간, 경기 단위 관중, 주자 상황, 수비·주루 지표 — 전부 원 데이터가 없다.

## 2. `web/`이 목표 사이트의 구현체인가

### 판정: **아니다. 네비게이션 뼈대만 목표 사이트를 본떴고 내용은 껍데기다.**

가설을 지지하는 근거는 하나뿐이고, 반증이 다섯 가지다.

**지지 근거**
- 네비 라벨이 8개 겹친다: HOME · 일정 · 팀/순위 · 타자 · 투수 · 이동거리 · 관중 · 경기시간.
- 시즌 셀렉터가 `vb-data.js:VB_YEARS`로 2026→1982 45년을 그린다(목표 사이트와 같은 범위).
- 파일명 `vb-data.js`의 `vb` = visual baseball로 읽힌다.

**반증**
1. **네비가 실제로는 다르다.** `web/index.html`의 네비는 10개이고 목표 사이트에 없는 `핫/콜드존`·`AI Lab`이 있으며, 목표 사이트의 `DAILY`가 **없다**. IA를 참고했지 복제하지 않았다.
2. **`distance.html`은 이동거리를 계산하지 않는다.** `metric-page.js:renderDistanceRows()`는 `kbo_schedule_{season}.csv`를 `away_team`으로 묶어 **원정 경기 수와 방문 구장 개수**를 세는 게 전부다. km이 한 글자도 없다. 목표 사이트의 총 이동거리·경기당 평균·최장/최단 원정·구장간 거리 매트릭스·경로 애니메이션 중 **0개** 구현. 라벨만 같다.
3. **타자/투수 페이지의 깊이 차가 10배다.** `batting.js`는 `kbo_hitter_metrics_{season}.csv`를 정렬해 **11열짜리 표 하나, 상위 80행**을 그린다. 목표 사이트 타자 페이지는 표 3모드(기본 18열 / 고급 16열 / 구종별) + 차트 19종 + 5인 비교다. `pitching.js`도 12열 표 하나뿐.
4. **관중·경기시간도 표뿐이다.** `attendance.html` = 표 1개(팀/관중/경기수/평균/갱신일). 목표 사이트 = 게이지 + 요일별 + 연도추이 + 팀별 비교 + bump chart + 월×연 히트맵. `gametime.html` = 표 2개. 목표 사이트 = 차트 7종 + top10 표 2개.
5. **정체성 자체가 다르다.** `web/index.html`의 `<title>`은 `AI Baseball Lab`, hero 카피는 "Portfolio Concept · 단순 데이터 시각화를 넘어, 야구팬이 질문하면 AI가 근거를 보여주는 실험실". 하드코딩된 선수 이름("김도영", "김도영 vs 노시환")도 그대로 남아 있다. 목표 사이트의 구현체가 아니라 **우리 프로젝트의 1세대 정적 프론트**다.

### 부수 판정: **React가 `web/`보다 뒤처져 있지도 않다.**

파일 타임스탬프도 `web/` 6/10~6/11 → React 6/22~ 순이고, 겹치는 8화면 중 6화면에서 React가 더 많은 것을 그린다. `web/`이 앞선 것은 **"페이지가 존재한다"는 사실 3건과 시즌 셀렉터 범위, RAG UI 1건**뿐이다.

### 이 판정이 로드맵에 미치는 영향

PLAN T4("`web/` 전용 화면 이전")의 전제가 틀렸다. 이전할 가치가 있는 것은 다음 3건뿐이다.

- `lab.html` → RAG 화면 (T5와 동일 작업. **로직도 재사용 가능**)
- `attendance.html`·`gametime.html` → 표 자체는 3분이면 다시 짜는 수준. **이식이 아니라 재작성**이 맞다.
- `distance.html` → **이식 대상이 아니라 폐기 대상.** 이름만 맞고 내용은 없다.

`web/`은 T3(Docker 프론트 교체) 이후 남길 이유가 없다.

## 3. 격차 목록

각 항목: 목표 사이트가 하는 것 → 우리 상태 → **우리 데이터로 지금 만들 수 있는가**(파일·컬럼 명시) → 난이도.

### G-01. 순위표 확장 · 난이도 **S** · 이미 있는 컬럼이 화면에 없음

| | |
| --- | --- |
| 목표 | 순위표 18열(순위·팀·G·승·패·무·승률·게임차·**5위와의 차·홈기록·원정기록·연속·최근10·득점·경기당득점·실점·경기당실점·득실차**), 홈 성적 표·원정 성적 표 별도, 피타고리안 승률, 상대전적 매트릭스, 공수 산점도(득점×실점, OPS×ERA), 팀 지표 히트맵, 다팀 레이더 |
| 우리 | `Standings.jsx`는 **8열**(순위/팀/경기/승/패/무/승률/게임차). `StandingsTable.jsx:13-20` 확인. |
| 데이터 | **전부 있다.** `data/raw/kbo_official/kbo_team_rank_2026.csv`에 `최근10경기`·`연속`·`홈`·`방문` 컬럼이 이미 있고 API(`/api/standings`)가 이미 서빙 중이다. 득점/실점/득실차·홈원정 분해·상대전적은 `data/processed/kbo_team_games_2026.csv`(`Team`,`Opponent`,`HomeAway`,`RunsFor`,`RunsAgainst`,`RunDiff`,`Result`, 1152행) 집계로 전부 나온다. 피타고리안도 `RunsFor`/`RunsAgainst`만 있으면 된다. |
| 못 하는 것 | **PO 진출 확률 시뮬레이션·최종순위 분포 예측** — PLAN 3절 명시적 비목표(예측 모델링). **RE24(주자·아웃별 기대득점)** — 투구 데이터에 베이스 상태가 없다. **팀 수비 지표**(FPCT/TC/PO/A/E/DP/PB/도루저지) — 수집 안 함. **팀 주루 지표**(SBA/OOB/PKO) — 수집 안 함. **도루 시도 패턴(카운트/이닝/투수 손별)** — 투구 데이터에 도루 이벤트가 없다. |

> **이 항목이 가장 싼 격차다.** API 변경 0, 크롤러 0, 새 CSV 0.

### G-02. 이동거리 · 난이도 **M** · 상수 하나만 추가하면 됨

| | |
| --- | --- |
| 목표 | 총 이동거리·리그평균·최대/최소·경기당 평균·최장/최단 원정, 구장간 거리 매트릭스(km), 원정 경로 애니메이션 지도(재생/속도/경기일 슬라이더/팀 토글), 2001~2026 |
| 우리 | 없다. `web/distance.html`은 거리를 계산하지 않는다(2절 반증 2번). |
| 데이터 | **거리 데이터는 0이다** — `grep -rniE "lat|lon|위도|좌표"` 결과 좌표는 전부 `PlateX/PlateZ`(투구 위치)뿐. **그러나** 필요한 입력이 상수 하나다: `kbo_schedule_2026.csv`의 `Ballpark` 값은 10종(고척·광주·대구·대전·문학·사직·수원·잠실·창원·포항)이고, `kbo_team_games_2026.csv`에 `Date`·`Team`·`HomeAway`·`Ballpark`가 전부 있다 → **구장 10곳의 위경도를 상수로 박으면 팀별 시즌 이동 경로와 총 km가 그대로 계산된다.** 구장간 거리 매트릭스도 같은 상수에서 나온다. |
| 못 하는 것 | **과거 시즌(2001~2025)** — `kbo_team_games`·`kbo_schedule`이 2026뿐이다. 지도 애니메이션은 지도 라이브러리 = 새 의존성(IDEAS가 이미 기각한 항목). **표 + 거리 매트릭스까지면 난이도 S**, 지도까지 가면 M~L. |

> `web/distance.html` 때문에 "우리에게 이동거리 데이터가 없다"고 알려져 있었지만, 실제로는 **10줄짜리 좌표 상수 하나가 없었을 뿐**이다.

### G-03. 관중 심화 · 난이도 **S**(가능분) / **L**(불가분) · 데이터가 얕다

| | |
| --- | --- |
| 목표 | 총/평균/최다/최소 관중, 인기 최고·최저 구단, 팀별 홈 평균 게이지(수용률), **요일별** 평균, **2001~ 연도별 추이**, 팀별 연도 비교 라인, 관중 순위 bump chart, **연×월 히트맵** |
| 우리 | 전용 화면 없음. `Home.jsx` 박스 2개(총 관중·최다 관중 팀). `web/attendance.html`에 표 1개. |
| 데이터 | `data/raw/kbo_official/kbo_attendance_2026.csv`(10행, 시즌 합계) + `kbo_attendance_monthly_2026.csv`(55행, `Season,Month,Team,Attendance`). **가능**: 팀×월 히트맵, 팀별 총/월평균, `kbo_schedule_2026.csv`의 `home_team` 카운트로 나눈 홈경기당 평균, 팀 순위 막대. |
| 못 하는 것 | **연도별 추이·bump chart·팀별 연도 비교** — 관중 CSV가 **2026 한 시즌뿐**이다(`cut -d, -f1 ... | sort -u` → `2026`만). **요일별 평균, 최다/최소 관중 경기, 수용률 게이지** — 관중이 **경기 단위가 아니라 팀×월 합계**라서 요일로 쪼갤 수 없고, 구장 정원 데이터도 없다. 전부 새 크롤러 선행(L). |

### G-04. 경기시간 심화 · 난이도 **S**(가능분) / **L**(불가분)

| | |
| --- | --- |
| 목표 | 평균 경기시간(전년비), 최장/최단 경기, **연도별 추이**, **월별**, **요일별**, 팀별 가로막대, **구장별**, **시작시간대별**, **10분 구간 분포 히스토그램**, 최장 10경기·최단 10경기 표 |
| 우리 | 전용 화면 없음. `Home.jsx` 박스 1개. `web/gametime.html`에 표 2개. `/api/game-time/yearly`는 **미사용 엔드포인트**. |

**요약**: 8개 중 **명확히 차별화되는 것은 #6 하나**, 확인 못 해서 차별화 가능성이 열린 것이 #3·#7, 나머지 5개는 목표 사이트에 대응물이 있다. 대응물이 있다는 게 하지 말라는 뜻은 아니다 — **#1은 접근 자체가 다르고(확률 vs 매직넘버), #2는 열세를 정직하게 드러내는 쪽이 오히려 신뢰를 산다.**

## 6. 권장 순서

정렬 기준 세 가지, 순서대로 적용:
**(1) 데이터가 이미 있는가** > (2) 목표와의 격차가 큰가 > (3) 지금 안 하면 가치가 떨어지는가.

| 순 | 할 것 | 근거 | 난이도 |
| --- | --- | --- | --- |
| 1 | **순위표 확장** (G-01) — 최근10·연속·홈/원정 열 노출, 득실차·피타고리안·상대전적 매트릭스, 홈/원정 표 분리 | **비용이 사실상 0이다.** 컬럼이 이미 CSV에 있고 API가 이미 서빙 중인데 8열만 그리고 있다. 목표 사이트 대비 격차가 가장 크면서 가장 싼 유일한 항목. IDEAS #4(상대전적)를 여기서 함께 흡수한다 | S |
| 2 | **IDEAS #1 가을야구 레이스** | **시간 민감.** 8월 말 5위 두산과 6위 NC가 갈리는 중이고 팀당 23~32경기 남았다. 9월엔 매일 열어보는 화면이고 10월엔 가치가 0이다. 1번의 산출물(잔여 경기·상대전적)을 그대로 재사용한다 | S |

## 7. 이 문서가 기존 문서에 요구하는 정정

기존 문서는 이번에 수정하지 않았다. 다음 개정 때 반영할 것:

1. **PLAN T4** — "`web/` 전용 화면 이전"의 전제가 틀렸다. `distance.html`은 이동거리를 계산하지 않으므로 **이전 대상이 아니라 폐기 대상**이고, `attendance`·`gametime`은 표 1~2개라 **이식보다 재작성이 싸다**(2절).
2. **PLAN 5절 갭 2번** — "`web/`에만 있는 화면(관중, 경기시간, 비거리)"에서 **비거리는 빼야 한다.** 그 화면은 존재하지 않는다.
3. **PLAN 4절 / README** — "과거는 1982~ 순위 데이터 보유"는 부정확하다. 과거 45시즌은 **선수 리더보드**이고 **팀 순위 CSV는 2026뿐**이다(IDEAS도 같은 지적).
4. **REQUIREMENTS FR-02 AC1** — 순위표에 `최근10경기`·`연속`·`홈`·`방문` 컬럼이 데이터에 있는데 화면에 없다. AC를 컬럼 단위로 조이거나 G-01을 별도 FR로 뗄지 결정 필요.
5. **REQUIREMENTS 5절 미사용 14개** — G-09(헤더 검색)를 붙이면 `players/search/{name}` 등이 소비처를 얻는다. "전부 지운다"가 유일한 답은 아니다.
