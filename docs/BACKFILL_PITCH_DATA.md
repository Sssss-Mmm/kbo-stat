# 네이버 투구 데이터 5년치(2021~2025) 백필 타당성 조사

작성일 2026-08-31 · 조사만 수행, 코드 변경 없음 · 프로브 산출물은 저장소 밖(스크래치패드)에만 저장

## 결론 한 줄

**조건부 가능.** 네이버는 2021~2025 전 시즌의 투구 단위 PTS 데이터를 지금도 서빙하고 스키마도 2026과 완전히 동일하다. 다만 (a) 수집기에 요청 간격 조절 인자가 없고, (b) `crawl()`이 범위 전체를 메모리에 쌓았다가 한 번에 저장해 중단 시 전량 유실되며, (c) 백필 후 `build_zone_metrics.load_pitches()`가 매일 1.2M행을 읽게 된다 — 이 3가지를 먼저 손봐야 실행 가치가 있다.

## 1. 수집기 구조 (`src/crawl_naver_pitch_zones.py`)

호출 순서 (모두 `https://api-gw.sports.naver.com`):

1. `GET /schedule/games?fields=all&fromDate={d}&toDate={d}&size=500&categoryId=kbo` — 하루 1회, 경기 목록
2. 경기별 `GET /schedule/games/{gameId}/record` — 1회, `pcode → name` 매핑 (`fetch_name_map`)
3. 경기별 `GET /schedule/games/{gameId}/relay?inning={1..12}` — 이닝 루프. `inning > 9`이고 `textRelays`가 비면 break → 9이닝 경기는 relay 10회

경기당 요청 ≈ **11회**(record 1 + relay 10), 날짜당 추가로 schedule 1회.

날짜/시즌 파라미터화 상태:
- **2026 하드코딩 없음.** `--date` / `--from-date` / `--to-date`만 받고, 기본값은 `current_kst_date()`.
- `Season`은 `season_from_game()`이 응답의 `seasonYear`(없으면 `gameDate[:4]`)에서 뽑는다 — 과거 시즌도 자동으로 맞는다.
- 파일명은 날짜 범위 접미사: `naver_kbo_pitches_{from}_{to}.csv`, `naver_kbo_zone_summary_{from}_{to}.csv`.
- `pause_seconds=0.15`는 `crawl_date()` 기본값이고 **`crawl()`에서 넘기지 않는다 → CLI로 조절 불가.**
- 상태 필터: `statusCode in {RESULT, ENDED, STARTED}`만 수집. 과거 날짜의 `BEFORE`는 전부 `cancel=True`(우천취소)로 확인됨 — 조용한 유실 아님.

## 2. 과거 시즌 응답 서빙 여부

서빙된다. 프로브에서 2021~2025 전 시즌이 정상 응답했고, 응답 키 집합이 2026과 사실상 동일하다.

- `ptsOptions` 키(좌표·궤적: `crossPlateX`, `y0/vy0/ay/z0/vz0/az`, `topSz`, `bottomSz`, `stance`, `inn`): **2021~2026 차이 0**
- `currentGameState` 키(`ball`, `strike`, `out`, `batter`, `pitcher`): **차이 0**
- `textOptions` 키(`stuff`, `speed`, `pitchResult`, `pitchNum`, `ptsPitchId`, `text`): 2021만 `currentPlayersInfo` 1개 부재 — **수집기가 쓰지 않는 필드라 무해**
- 산출 DataFrame 컬럼 35개가 2021~2026 전부 2026과 **완전 일치**
- 포스트시즌도 같은 엔드포인트로 나온다(`gameId=77771107KTLG02023`, `roundCode=kbo_ps_ks`, `categoryId=kbo`) → 현재 필터로 그대로 잡힌다

의존 필드는 전 연도에서 모두 존재하고 채워진다(아래 표).

## 4. 5년 전량 비용 추정

실측 기준값(실제 2026 데이터 132,469행 / 431경기에서 산출):
- 투구/경기 = **307.4**
- 바이트/행 = **261 B**
- 경기당 소요 = 104.5초 / 28경기 = **3.73초** (pause 0.15초)
- 경기당 요청 ≈ **11회**

| 항목 | 5시즌(2021~2025) 추정 |
|---|---|
| 경기 수 | 정규 720/시즌 × 5 = 3,600 + 포스트시즌 ~70 ≈ **3,670** |
| 투구 행 수 | 3,670 × 307.4 ≈ **1.13M 행** |
| pitches CSV 용량 | ≈ **295 MB** |
| zone_summary 포함 총 용량 | ≈ **315 MB** (요약본은 투구본의 약 6%) |
| 총 HTTP 요청 | 3,670 × 11 + 일자 schedule ~1,150 ≈ **41,600건** |
| 순차 소요 (pause 0.15s, 현재 기본값) | ≈ **3.8시간** |
| 순차 소요 (pause 0.5s, 권장) | ≈ **7.8시간** |
| 순차 소요 (pause 1.0s) | ≈ **13.4시간** |
| 단일 프로세스 RAM | 1.09 KB/행 × 1.13M ≈ **1.2 GB** (한 번에 돌리면 위험) |

디스크는 문제 없다(여유 865 GB).

**지금 방식 그대로면 현실적이지 않다.** 이유 3가지:
1. `crawl()`이 `frames` 리스트에 전 범위를 쌓았다가 마지막에 한 번 저장한다. 5시즌 단일 실행 = RAM 1.2 GB + 중간에 네트워크 예외 1번이면 **수 시간치 전량 유실**.
2. `pause_seconds`가 CLI로 노출되지 않아 41,600건을 0.15초 간격으로 때린다 — 차단 위험 구간.
3. 백필 후 `build_zone_metrics.load_pitches()`가 `naver_kbo_pitches_*.csv`를 **전부 읽고 concat한 뒤에야** 시즌 필터를 건다. 현재 39 MB/0.5초/164 MB RAM → 백필 후 **약 335 MB / 5초 / 1.4 GB RAM을 매일 새벽 2시마다** 반복한다.

## 5. 결손·품질 위험

- **비어 있는 시즌·기간 없음.** 2021~2025 프로브 전부 정상 응답, 좌표 결측률 0~0.5%로 2026과 동일 수준.
- **2026 결손 구간(6/29~7/28)은 지금도 서빙된다.** 스케줄 확인 결과 6/30·7/3·7/8·7/25·7/28 모두 `RESULT` 경기 존재. 7/14·7/20은 경기 자체가 0건(리그 휴식기)이라 결손이 아니다. 즉 이 한 달은 **복구 가능**하며, 대략 20 경기일 × 4.5경기 ≈ 90경기 ≈ 27,600행 ≈ 11분(pause 0.5s)이면 메워진다.
- **우천취소·더블헤더**: 취소 경기는 `statusCode=BEFORE` + `cancel=True`로 명확히 구분되고 수집기가 이미 건너뛴다. 더블헤더/서스펜디드는 `gameId` 접미 숫자(`...HTSK0` / `...HTSK1` / `...LGSS2`)로 구분되므로 `(GameId, PitchId)` dedupe가 정상 동작한다.
- **2020 이전 (참고 조사, 경기 1건씩만 프로브)**

  | 시즌 | 유효 경기 | 1경기 투구 행 | 좌표 결측 | 판정 |
  |---|---|---|---|---|
  | 2020 | 6/6 | 298 | 0% | 사용 가능 (코로나 무관중 시즌이나 720경기 정상 소화) |
  | 2019 | 5/5 | 297 | 0.67% | 사용 가능 |
  | 2017 | 5/5 | 306 | 0% | 사용 가능 |
  | 2014 | 4/4 | 337 | **100%** | **사용 불가** — 문자중계는 있으나 PTS 좌표가 없다 (`ptsFlag`에 `0` 혼재) |

  PTS 좌표의 하한선은 2015~2017 사이 어딘가다. 필요하면 2015·2016을 1경기씩 더 찍어 확정하면 된다. 2020까지 넓히면 6시즌 ≈ 1.35M행 ≈ 355 MB.
- **품질 위험 한 가지**: `IsHit`은 타석 결과 텍스트를 한글 키워드(`안타`/`루타`/`홈런`, 제외어 `실책`/`야수선택`)로 판정한다. 전 연도 표현이 동일함을 프로브에서 확인했지만, 이 판정은 스키마가 아니라 **문구**에 의존하므로 백필 후 연도별 `IsHit/IsInPlay` 비율(프로브 기준 30~37%)을 반드시 눈으로 검산해야 한다.

### 6.2 분할 단위

**월 단위 청크.** 시즌당 8청크(03~11월, 11월은 포스트시즌), 5시즌 = **약 40청크**.

- 청크 1개 ≈ 120경기 ≈ 36,900행 ≈ 9.6 MB ≈ **15분**(pause 0.5s)
- 파일명이 범위로 결정되므로 청크마다 별도 파일 → **같은 청크 재실행 = 같은 파일 덮어쓰기 = 멱등**
- 경기 없는 날은 `fetch_games`가 빈 목록을 주고, 청크 전체가 0행이면 `crawl()`이 `save_csv`를 아예 호출하지 않는다 → 비시즌 범위를 잘못 넣어도 `EmptyDatasetError`가 나지 않는다

```
# 예시 (한 청크)
python src/crawl_naver_pitch_zones.py --from-date 2023-05-01 --to-date 2023-05-31 --pause 0.5
```

### 6.3 요청 간격·부하

- `--pause 0.5` (이닝 요청 사이). 5시즌 총 7.8시간, 초당 평균 1.5요청 미만.
- **하루 최대 2청크(약 30분·2,600요청)** 로 제한하고, 새벽 cron(02:00)과 겹치지 않는 시간대에 돌린다. 40청크 = 약 3주.
- 급하면 시즌 1개(8청크, 약 2시간)를 야간 1회에 몰아도 되지만, 그 이상은 권장하지 않는다.

### 6.4 중단·재개

- 진행 상태 = `data/raw/naver/` 파일 목록 그 자체. 청크 파일이 있으면 완료, 없으면 미완.
- 실패 청크는 **그 청크만** 재실행. 다른 청크에 영향 없다.
- 재시도 정책: 청크 실패 시 **즉시 재시도 금지**(NFR-09). 최소 10분 대기 후 1회만 재시도하고, 두 번째도 실패하면 그날은 중단하고 응답 본문을 확인한다. 429/403이 보이면 즉시 전면 중단.

### 6.5 V-08 (`src/csv_guard.py`, 전일 대비 50% 급감 거부) 대응

동작 원리를 먼저 짚으면 — `_check_row_drop`은 **같은 경로에 파일이 이미 있을 때만** 비교한다. 백필 청크는 매번 새 파일명이라 대부분 비교 자체가 일어나지 않는다.

| 상황 | `check` | 이유 |
|---|---|---|
| 신규 청크 최초 수집 | 기본값 `True` (그대로) | 기존 파일 없음 → V-08 미발동. 끌 이유 없다. |
| 실패 청크 **동일 범위 재실행** | 기본값 `True` **유지** | 1차가 부분 성공해 행이 있었는데 2차가 절반 미만이면 그건 진짜 사고다. V-08이 막는 게 맞다. |
| 재실행이 정당하게 적게 나오는 경우(1차에 중복 범위가 섞여 있었음이 확인됨) | **`check=False`** | 사람이 원인을 확인한 뒤에만. 무조건 끄지 말 것. |
| `build_zone_metrics` 과거 시즌 산출 (`kbo_batter_zones_2021.csv` 등) | 기본값 `True` | 최초 생성이라 비교 대상 없음. |
| `build_zone_metrics --year 2026` 백필 직후 | 기본값 `True` | 행이 늘기만 하므로 V-08 미발동. |

요약: **백필에서 `check=False`를 상시로 켜지 마라.** 원인이 확인된 재실행 1건에 한해, 그 실행에서만 쓴다.

### 6.6 실행 순서

1. **리허설**: 2026 결손 구간 `--from-date 2026-06-29 --to-date 2026-07-28` (약 11분). 여기서 행 수·결측률·`IsHit` 비율을 검산한다. 이게 통과하면 5년치도 통과한다.
2. `python src/build_zone_metrics.py --year 2026` 재실행 → 로그의 `coverage=N일` 이 91 → 약 111로 늘어나는지 확인.
3. 최신 시즌부터 역순(2025 → 2021)으로 월 청크 진행. 가치가 높은 시즌을 먼저 확보해 중간에 멈춰도 손해가 적다.
4. 시즌 하나가 끝날 때마다 `build_zone_metrics.py --year {시즌}` 1회. 산출 로그의 `coverage=N일 (min~max)` 를 기록해 **표본 기간이 다른 시즌이 같은 표처럼 보이지 않게** 한다.
5. 과거 시즌 존 CSV가 생기면 `kbo-dashboard/backend/routers/zones.py`(`kbo_batter_zones_{season}.csv` 템플릿)가 자동으로 읽는다 — 라우터 수정 불필요. 다만 프론트에 시즌 선택 UI가 없으면 노출되지 않으니, 프론트 담당과 조율할 것.

- **`--pause` 없이(=0.15초 고정) 5시즌 연속 실행 금지.** 리허설 한 달치까지는 몰라도 전량은 안 된다.
- **`--from-date 2021-03-01 --to-date 2025-11-30` 같은 단일 대범위 실행 금지.** RAM 1.2 GB + 중단 시 전량 유실 + 300 MB짜리 CSV 1개가 남아 재수집 단위가 사라진다.
- **실패 시 즉시 반복 재시도 금지.** 429/403이면 그날은 끝. 재시도 루프가 차단을 부른다.
- **cron 시간대(02:00 KST) 침범 금지.** 일일 갱신과 겹치면 하루 1회 원칙이 깨지고 두 프로세스가 같은 디렉터리에 쓴다(`flock`은 `update_kbo_daily.sh`만 보호한다 — 수동 백필은 락 밖이다).
- **`data/`에 프로브·실험 산출물 남기지 말 것.** 이번 조사 산출물은 전부 스크래치패드에만 있고 `data/`는 건드리지 않았다.
- **`csv_guard`를 `check=False`로 상시 우회 금지.** 6.5 참조.
