## 정렬 기준

`팬 임팩트 ÷ 구현비용` 내림차순. 동점이면 아래 순서로 가른다.

1. **이미 가진 데이터로 되는가** — 새 크롤러가 필요하면 후순위. 데이터 없는 아이디어는 아이디어가 아니라 소원이다.
2. **기존 엔드포인트로 되는가** — 프론트만 고치면 되는 것 > 새 API가 필요한 것 > 새 파생 파이프라인이 필요한 것.
3. **원 사이트에 없는가** — KBO 공식·네이버에서 그대로 볼 수 있는 화면은 만들 이유가 없다.

전 항목 공통 제약: React 앱(`kbo-dashboard/frontend`)에만 넣는다(C-04). 새 npm 의존성 0개.
차트는 기존 `components/charts/{RankRace,Scatter,Beeswarm}.jsx`, `components/{MiniTable,ZoneHeatmap}.jsx`, `lib/{format,teamColors}.js`를 재사용한다.

### 데이터 출처

| 값 | 출처 |
| --- | --- |
| 승·패·무·승률 | `GET /api/standings` |
| 일별 순위 재구성 | `GET /api/team-games` → `Date`, `Team`, `Win`/`Loss`/`Draw` 누적 |
| 잔여 경기 수 | `144 − standings.경기` (정석). 검증: 각 팀 `경기 + 미래일정` = 141~144, 차이는 미재편성 취소분 |

### 난이도: S (2~4일)

새 백엔드 코드 0줄. `Standings.jsx`(현재 54줄)에 섹션 하나와 계산 함수 하나.
순위 재구성은 `team_games`를 날짜순 누적하는 `reduce` 한 번 — Teams 페이지가 이미 같은 데이터를 통째로 받아 클라이언트에서 필터링하는 패턴을 쓴다.

### 엣지 케이스

- **비목표 경계**: 승률 기반 확률·시뮬레이션은 만들지 않는다(PLAN 3절 "예측 모델링" 비목표). 매직넘버는 잔여 경기로부터의 **결정론적 산수**이며, 화면에 그 사실을 명시한다.
- 시즌 초반(4~5월)에는 매직넘버가 무의미 → **잔여 60경기 초과면 매직넘버 열을 숨기고** 순위 곡선과 잔여 일정만 보여준다.
- 취소 경기가 재편성되면 잔여 수가 하루 사이 바뀐다 → 잔여 수는 항상 `144 − 경기수`로 재계산(캐시 금지).
- 무승부는 승률 계산에서 제외(KBO 규정) — `Win/(Win+Loss)`. `team_games`의 `Draw`를 분모에 넣지 않는다.
- 오프시즌·포스트시즌: 섹션 전체를 감추고 "정규시즌 종료 · 최종 순위" 문구(FR-12 정합).
- 5위 경계 동률: 승률 동률이면 상대전적 우선 규정까지 재현하지 않는다. "동률" 배지로 표기하고 단정하지 않는다.

### AC

1. 3/28~오늘까지 매 경기일의 순위 곡선이 그려지고, 곡선의 마지막 날 순위가 `/api/standings`의 순위와 10팀 전부 일치한다.
2. 각 팀의 잔여 경기 수가 `144 − 경기수`와 일치하고, 합계가 리그 전체 잔여 경기의 2배와 ±3 이내다.
3. 매직넘버 열은 잔여 경기가 60을 넘는 시점에는 렌더링되지 않는다.
4. "남은 맞대결" 목록에 `Note`가 `-`가 아닌(취소된) 경기가 한 건도 포함되지 않는다.
5. 매직넘버 산식과 "예측 아님" 문구가 화면에 표시된다.

### 난이도: M (1~2주)

집계 자체는 하루면 끝난다. 비용은 **과거 데이터의 결손 처리**에 있다.

### 엣지 케이스

- **시즌 길이가 다르다.** 1982년 80경기 vs 2026년 144경기. 누적 기록(HR·RBI) 랭킹에는 시즌 경기수를 함께 표시하고, 비율 기록(AVG·ERA)만 무보정 비교를 허용한다.
- **규정 충족자만 있다.** 리그 평균이 아니라 "그 해 리더보드에 든 선수"다. 화면에 이 한계를 문장으로 명시한다("리그 평균 아님").
- 진행 중 시즌(2026)은 랭킹에 넣되 `진행 중 115/144` 배지를 붙인다. 안 붙이면 미완성 기록이 역대 랭킹에 섞인다.
- 팀명이 시대별로 다르다(MBC·해태·현대·넥센). **매핑하지 않고 당시 팀명 그대로** 보여준다 — 팬에게는 그게 맞고, 매핑은 논쟁거리다.
- 1982년 백인천 `.412`는 298타석이다. 타율 랭킹에는 `min_pa` 기본값(예: 규정 타석 = 경기수×3.1)을 두되, 값을 화면에서 조절 가능하게.
- 동일 기록 동순위 처리(53홈런 2명 → 공동 3위).

### AC

1. `stat=HR` 요청 시 1위가 2003 이승엽 56이다.
2. `stat=AVG&min_pa=300` 요청 시 1982 백인천 `.412`가 포함되고, `min_pa=400`이면 제외된다.
3. 2026 시즌 행에는 진행 중 배지가 표시되고 완료 시즌 행에는 표시되지 않는다.
4. 45개 시즌 전부가 최소 1행 이상 포함된다(누락 연도 없음).
5. `kbo_history_leaders.csv`가 없어도 API는 500이 아니라 404로 응답한다.

**#2를 먼저 하면 구종 블록과 타석 로그가 공짜로 딸려온다** — 그래서 #2 다음에 둔다.

### 엣지 케이스

- 동명이인: `(선수명, 팀)`으로도 안 갈리면 프로필 블록을 비우고 스탯만 표시. **틀린 프로필을 붙이는 것보다 비우는 게 낫다.**
- 시즌 중 이적: 등록 명단은 최신 팀, 시즌 스탯은 누적 → 팀 표기가 어긋날 수 있다. 스탯 카드의 팀을 우선한다.
- 투구 데이터 결손일의 타석은 로그에 없다 → `91/122일` 표기 고정.
- 규정 미달 선수(예: 5타석): `리그 내 위치` 막대를 숨기고 "표본 부족" 문구.
- 투수를 선택하면 존 히트맵의 의미가 뒤집힌다(피안타율) → 라벨을 role에 따라 바꾼다(`Zones.jsx`에 이미 있는 규칙 재사용).
- 외국인 선수 생년월일 결손 가능 → 나이 미표시.

### AC

1. 선수 이름 클릭 시 패널이 열리고, 표시된 AVG/HR이 표 행의 값과 일치한다.
2. WAR·wRC+·wOBA·WPA 네 지표가 모두 표시된다(현재 어느 화면에도 없는 값).
3. 존 데이터가 없는 선수는 히트맵 자리에 "존 데이터 없음"이 뜨고 패널의 나머지는 정상 표시된다(NFR-06).
4. 프로필 조인 실패 시 나이·신장 자리가 비고, 콘솔 에러 없이 패널이 유지된다.
5. 타석 로그에 수집일 커버리지가 표시된다.

## #6 볼카운트 야구 — 초구부터 치는 타자, 2S에서 버티는 타자 · 난이도 S (#2 선행 시)

> **훅** — "쟤는 왜 맨날 초구에 치다 죽지?" / "2스트라이크 몰리면 진짜 못 치나?"

야구 중계가 매일 떠드는 이야기인데 **숫자로 확인할 수 있는 곳이 없다.**

### 화면 설계

`구종` 페이지(#2)의 세 번째 탭. 별도 데이터 파이프라인 없음.

```
│ [Beeswarm 재사용 · 343명 분포]       │ │      0S    1S    2S        │
```

### 데이터 출처

`naver_kbo_pitches_*.csv`의 `Ball`, `Strike`, `PitchNo`, `IsSwing`, `PitchResult`, `IsHit`, `IsInPlay`.
**#2의 `build_pitch_arsenal.py`에 `CountBucket` 차원을 이미 넣어두므로 추가 수집·추가 파이프라인이 없다.**
API도 `/api/pitch-arsenal`에 `group=count` 파라미터를 얹으면 된다 — 새 엔드포인트 불필요.

### 난이도: S (#2 완료 후 2~3일 / #2 없이 단독이면 M)

### 엣지 케이스

- 카운트 셀 12개 × 선수 → 셀당 표본이 급감한다. **선수 단위는 초구·2S 두 버킷만** 노출하고, 12칸 매트릭스는 리그 단위로만 보여준다.
- 타석 50개 미만 타자는 목록에서 제외.
- `Ball`/`Strike` 컬럼은 그 투구를 **던진 직후** 값이다(검증: 1구 스트라이크 → Strike=1). 던지기 **전** 카운트를 쓰려면 한 칸 시프트가 필요하다 — 이걸 틀리면 전 지표가 어긋난다. 구현 시 자체 점검 필수(NFR-18).
- 결손 구간 배지는 #2와 동일하게 공유.

### AC

1. 리그 초구 스윙률이 20~40% 범위 안이다(야구 상식 범위 밖이면 카운트 시프트 버그).
2. 카운트 매트릭스에서 3B-0S 타율이 0B-2S 타율보다 높다(타자 유리 카운트가 실제로 유리하게 나온다).
3. 타석 50개 미만 타자가 목록에 없다.
4. 카운트 시프트 로직에 `assert` 기반 자체 점검이 있고, 알려진 타석 1개로 검증된다.

## #7 구장 도감 — 잠실은 정말 투수 구장인가 · 난이도 S

> **훅** — "우리 팀은 왜 원정만 가면 점수가 터지지?"

파크 팩터는 야구 팬이 좋아하는 개념인데 KBO에서 볼 수 있는 곳이 사실상 없다.

### 화면 설계

PLAN T4(`web/` 관중·경기시간 이식)가 만들 화면에 **같이 넣는다.** 별도 페이지를 새로 만들지 않는다.

```
┌ 구장별 득점 환경 ──────────────────────────────────────────┐
│ 구장   경기  경기당 총득점  리그대비  평균 경기시간  평균 관중 │
│ ──────────────────────────────────────────────────────── │
│ 대구    79    11.2        +14%       3:12       14,200   │
│ 잠실   156     8.6        -12%       3:05       18,900   │
│ 사직    77    10.4         +6%       3:09       12,100   │
│ ...                                                       │
│ 포항     3     9.7          —        3:01        9,800   │
│         ↑ 표본 3경기 · 순위에서 제외                        │
│                                                           │
│ ⓘ 파크 팩터가 아니라 '경기당 총득점의 리그 대비 비율'이다.    │
```

### 데이터 출처

- 득점 환경: `GET /api/team-games` → `Ballpark`, `RunsFor`+`RunsAgainst`를 경기(`GameId`) 단위로 접어 구장별 평균. **기존 API.**
- 경기시간: `GET /api/game-time/team` (기존, 화면 미사용)
- 관중: `GET /api/attendance` (기존, 화면 미사용)

구장별 경기 수 실측: 잠실 156 / 창원 81 / 광주 80 / 대구 79 / 수원 79 / 대전 78 / 사직 77 / 문학 76 / 고척 73 / 포항 3.

### 난이도: S (2~3일, T4 화면 위에 얹는 경우)

계산은 groupby 한 번. 표는 `MiniTable` 재사용.

### 엣지 케이스

- **포항 3경기.** 표본 30경기 미만 구장은 표에 표시하되 순위·색칠에서 제외하고 회색 처리.
- **잠실은 LG·두산 공용**이라 156경기다. 홈팀별로 쪼개지 않고 구장 단위로만 집계한다(구장 효과가 목적이므로).
- 진짜 파크 팩터는 홈/원정 보정이 필요하다. 하지 않는다 — **하지 않았다는 사실을 화면에 쓴다.** 보정 없는 숫자에 "파크 팩터"라는 이름을 붙이는 게 더 나쁘다.
- 시즌 초반(구장당 20경기 미만)에는 섹션 전체를 "표본 축적 중"으로 대체.
- 관중은 팀 단위 데이터라 구장 단위와 1:1이 아니다(잠실). 잠실 관중은 두 팀 합으로 표기하고 각주.

### AC

1. 구장별 경기수 합이 리그 총 경기수와 일치한다.
2. 30경기 미만 구장(포항)은 회색으로 표시되고 리그 대비 % 열이 비어 있다.
3. "보정 없음" 문구가 표시된다.
4. `/api/attendance` 또는 `/api/game-time/team` 하나가 실패해도 득점 환경 열은 정상 표시된다(NFR-06).

## #8 타구 성향 — 당겨치는 타자, 밀어치는 타자 · 난이도 M

> **훅** — "저 타자한테 시프트 걸면 되는 거 아냐?"

`AtBatText`에 타구 방향이 그대로 한국어로 들어 있다: `좌익수 앞 1루타`, `2루수 땅볼 아웃`, `우중간 2루타`, `좌익수 뒤 홈런`.
파싱만 하면 **타자별 타구 방향·타구 종류 분포**가 나온다. KBO·네이버 어디에도 없다.

### 화면 설계

`선수 상세 카드`(#5) 안의 블록 또는 `구종` 페이지 탭.

```
┌ 타구 성향 · 오스틴 (인플레이 312타구) ──────────────────┐
│            좌      중      우                           │
│   외야   ███ 31%  ██ 22%  █ 11%                        │
│   내야   ██ 18%   █ 9%    ██ 9%                        │
│                                                        │
│   땅볼 38% · 플라이 44% · 라인드라이브 등 기타 18%        │
│   당김 49% / 중앙 31% / 밀어침 20%  (우타 기준)          │
│   ⓘ 텍스트 파싱 · 분류 불가 6% 제외                      │
└────────────────────────────────────────────────────────┘
```

### 데이터 출처

`naver_kbo_pitches_*.csv` → `AtBatText`(타석 마지막 행), `BatterSide`(당김/밀어침 판정에 필요).
실측 상위 패턴: `삼진 아웃`(4765) `볼넷`(2527) `중견수 플라이 아웃`(1114) `2루수 땅볼 아웃`(1033) `좌익수 앞 1루타`(548) `좌익수 뒤 홈런`(202) `우중간 2루타`(165)...

파싱 규칙: 야수 포지션명(좌익수·중견수·우익수·유격수·1~3루수·투수·포수) + 방향 보조어(좌중간·우중간) + 타구 종류(땅볼·플라이·직선타·번트).
**#2의 타석 집계 파이프라인에 컬럼 2개(`HitDirection`, `BattedBallType`)를 추가**하는 형태 — 별도 파이프라인 아님.

### 난이도: M (1~2주)

파싱은 반나절이면 쓴다. 비용은 **커버리지 검증**이다. `삼진 아웃`·`볼넷` 같은 비타구 결과를 제외하고, 남은 텍스트의 몇 %가 분류되는지 실측해야 한다. 90% 미만이면 이 기능은 만들지 않는 게 맞다.

### 엣지 케이스

- **미분류 비율을 화면에 표시한다.** `분류 불가 6% 제외` 같은 문구 없이 100%인 척하면 안 된다.
- `포수 스트라이크 낫 아웃`(458건), `투수 희생번트`, `유격수 앞 땅볼로 출루`(실책성) 등 특수 케이스가 많다 → 타구 방향은 있지만 타격 결과가 아닌 것을 분리.
- 좌타/우타에 따라 "당김"의 방향이 반대다. `BatterSide`로 뒤집는다. 스위치히터는 타석별 `BatterSide`를 그대로 쓴다.
- 인플레이 타구 50개 미만 타자는 제외.
- 네이버 텍스트 표현이 바뀌면 미분류율이 뛴다 → **미분류율이 15%를 넘으면 화면에 경고 배지**를 띄운다(조용한 실패 방지, PLAN 4절 실패 모드와 동일한 철학).

### AC

1. 비타구 결과(삼진·볼넷·몸에 맞는 볼)를 제외한 `AtBatText`의 90% 이상이 방향으로 분류된다.
2. 미분류 비율이 화면에 표시된다.
3. 좌타자와 우타자의 "당김" 방향이 서로 반대로 계산된다(자체 점검 케이스 1개씩).
4. 인플레이 50타구 미만 타자는 목록에 없다.
5. 미분류율 15% 초과 시 경고 배지가 렌더링된다.
